# AI 建档 v3 · 后端现有方案迁移说明

本文针对后端当前的“五字段 + 本地词典 + 必要时调用 GLM”方案，说明如何迁移到已验收的 v3 目标。

## 1. 可以直接保留

以下属于正式服务基础设施，与 Demo 逻辑不冲突：

- 服务端持久化会话；
- 退出页面后继续后台处理；
- 重新进入时恢复完整状态；
- collecting / processing / review_pending / completed；
- requestId 幂等；
- 处理中禁止重复发送；
- 已确认档案和编辑草稿分离；
- 前端重连后重新拉取服务端状态。

## 2. 必须替换

### 五字段改为八字段

旧：

- 职业
- 兴趣
- 社交风格
- 聚会偏好
- 希望认识的人

新：

- occupation
- social_purpose
- social_style
- chat_topics
- activity_style
- schedule_preference
- stranger_story
- friend_description

不要把新字段再次合并回五个大类，否则无法对齐问题顺序、补聊和完整度。

### 删除本地词典优先分流

旧流程：

```text
简单回答 → 本地处理
复杂回答 → GLM
```

新流程：

```text
每次回答 → GLM
服务端校验 currentField 更新
```

原因：

- 本地词典会与 Prompt 的低质/模糊边界不一致；
- 容易漏掉自定义回答；
- 容易出现同一句话部分处理、部分丢失；
- 改问题时还要同步修改词典。

### 用户话术交给 GLM

旧方案由服务端模板生成确认语和下一题。新方案由 GLM 返回完整 `assistant_reply` 与 `quick_replies`。

服务端只校验：

- 是否问了正确字段；
- 是否只更新 currentField；
- 是否允许推进；
- 是否应该 wrap_up。

### 最终介绍改为 wrap_up

旧方案持续本地拼接介绍，结束时不再调用模型。

新方案结束时调用一次 GLM，生成更自然的总结和后续推荐方式。仅模型结果异常时使用本地 fallback。

### 模型失败不得静默推进

旧方案中，模型超时或格式错误可能按“没有有效回答”继续下一题。

新方案必须：

```text
失败 → 回滚 → 保持 currentField → 返回可重试状态
```

## 3. 需要重新确认的旧逻辑

### “都行”

旧方案可能本地识别为有效答案。v3 中：

- 当前题确实允许“都行/看情况”且语义明确时可以 clear；
- 单纯说“随便吧、都行、不知道”来应付问题时是 low_quality。

不要只靠关键词判断，要结合当前题与上下文交给模型。

### 多字段提取

旧方案允许一句话更新多个字段。v3 为了状态稳定，只接受 currentField。

例如当前问职业：

> 我是程序员，平时喜欢跑步。

本轮只写 occupation=程序员。跑步保留在聊天历史，后续进入 chat_topics 时再确认。

### 用户拒绝

- “跳过 / 不方便说” → skip 当前题并推进。
- “随便吧 / asdfgh” → low_quality，停留当前题。
- “滚 / 别问了 / 不聊了” → ask_end，立即收束。

## 4. 推荐迁移步骤

1. 保留现有会话表、状态恢复和 requestId 机制。
2. 新增 v3 草稿结构和 fieldQueue。
3. 接入新的 system-prompt.js。
4. 移除本地词典对画像答案的最终决定权。
5. 将 GLM 输出升级为 answer_status + user_signal + assistant_reply。
6. 只允许写 currentField。
7. 实现统一状态转换和完整度。
8. 增加 wrap_up。
9. 前端改为展示服务端 quick_replies 和 profile_complete。
10. 按正式交接文档的 15 项用例验收。

## 5. 迁移完成的判断标准

只有同时满足以下条件才算对齐：

- 修改 Prompt 后，不需要同步修改服务端题目模板或答案词典；
- 自定义答案不会被预设选项拒绝；
- AI 问的题与后台 currentField 始终一致；
- 模型失败不会丢答案或推进；
- 跳过可以收束，但不会误判匹配完整；
- 补聊只问未齐字段；
- 最终介绍来自模型，fallback 只做兜底；
- 正式服务的退出恢复和幂等能力仍然保留。
